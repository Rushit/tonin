# Database

A connection URL and a telemetry label — your DB client crate does the rest.

## What you get

- A `DATABASE_URL` env var injected into the service container at deploy time, read from the
  platform's database Secret (the **platform contract**, below). tonin does not run databases.
- Optional `sslmode=verify-full`: the server CA is mounted and the URL carries the TLS parameters.
- A network-policy egress rule to the database pods.
- A `db.system` label (`postgres` / `mysql` / `sqlite` / `clickhouse`) attached to spans so DB calls show up correctly in your tracing backend.
- Migrations as a pre-install/pre-upgrade hook Job or an initContainer, chosen per environment.
- A `Database` trait you can implement to carry the connection URL + system label uniformly across services — typed access stays in your DB client crate (sqlx, sea-orm, tokio-postgres). The framework does not ship an ORM.

## Trait surface

From `crates/tonin-sdk/src/traits/database.rs`:

```rust
#[async_trait]
pub trait Database: Send + Sync + 'static {
    /// Connection URL — e.g. `postgres://user:pass@host:5432/db`.
    /// Default impls read this from the `DATABASE_URL` env var the
    /// deployment template injects.
    fn url(&self) -> &str;

    /// Optional framework-managed pool. Default `None`.
    fn pool(&self) -> Option<&dyn AnyPool> { None }

    /// Span attribute `db.system` — one of:
    /// "postgres" | "mysql" | "sqlite" | "clickhouse".
    fn system(&self) -> &'static str;
}
```

`AnyPool` is a marker trait reserved for a future framework-managed pool. Today, it returns `None` and you bring your own pool (sqlx::PgPool, etc.).

## Selecting an impl

Declare the database in `tonin.toml`:

```toml
[database]
engine = "postgres"
```

`[database]` is a **reference to the platform contract**, not a database tonin renders. The
platform layer (CNPG on a VPS cluster, or OpenTofu-created Secrets for a managed database) provides,
in the service's namespace:

| Contract | Default (`<svc>` = `[service].name`) |
|---|---|
| Secret with the connection URL | `<svc>-pg-app`, key `uri` |
| Secret with the server CA | `<svc>-pg-ca`, key `ca.crt` |
| Database pods (for network policy) | label `cnpg.io/cluster=<svc>-pg`, port 5432 |

These are the names CNPG uses for `Cluster <svc>-pg` (`<cluster>-app`, `<cluster>-ca`, the
`cnpg.io/cluster` pod label). What `tonin helm generate` renders from it:

- `DATABASE_URL` from `secretKeyRef` `<svc>-pg-app` / `uri` on the server container, the
  migration initContainer and the migration Job;
- an egress rule in the service's CiliumNetworkPolicy to `cnpg.io/cluster=<svc>-pg` on 5432;
- no StatefulSet, Service or Secret for the database. Charts generated by earlier tonin versions
  have `templates/db-*.yaml` / `cache-*.yaml`: `generate` deletes them, `helm check` reports them.

### Overrides

Every field can be set on `[database]` and overridden per environment in `[database.<env>]`:

| Field | Default | Meaning |
|---|---|---|
| `engine` | (required) | `postgres`, `mysql`, `sqlite`, `clickhouse`, or `none` (no database in this env) |
| `env` | `DATABASE_URL` | env var the URL lands in |
| `cluster` | `<svc>-pg` | CNPG cluster name; the defaults below derive from it (Postgres only) |
| `secret` | `<cluster>-app` | Secret holding the URL |
| `key` | `uri` | key of the URL in `secret` |
| `tls` | `"none"` | `"verify-full"`: mount the CA and verify the server (Postgres only) |
| `ca_secret` | `<cluster>-ca` | Secret holding `ca.crt` |
| `labels` | `{ "cnpg.io/cluster" = "<cluster>" }` | pods egress is allowed to; `{}` renders no rule |
| `namespace` | the service's | namespace of those pods (`{env}` is substituted) |
| `port` | engine default (5432) | egress port |
| `url` | — | per env only: a literal URL instead of the Secret (see *Dev*) |

Engines other than Postgres default to Secret `<svc>-db` and label
`app.kubernetes.io/name=<svc>-db`; `sqlite` gets no egress rule.

A service whose code reads a different variable — e.g. `zvectorlabs-api` reads
`PLATFORM_DATABASE_URL` — sets `env`:

```toml
[database]
engine = "postgres"
env    = "PLATFORM_DATABASE_URL"   # Secret zvectorlabs-api-pg-app, key uri
```

### TLS (`verify-full`)

```toml
[database.prd]
tls = "verify-full"
```

mounts **only** the `ca.crt` key of `<svc>-pg-ca` at `/etc/pg-ca/ca.crt` (read-only) and composes
the URL with Kubernetes `$(VAR)` expansion:

```yaml
- name: TONIN_PG_URI            # the raw uri, declared first
  valueFrom: { secretKeyRef: { name: identity-pg-app, key: uri } }
- name: DATABASE_URL
  value: "$(TONIN_PG_URI)?sslmode=verify-full&sslrootcert=/etc/pg-ca/ca.crt"
```

The contract's `uri` must not carry a query string of its own (CNPG's does not), since the
parameters are appended with `?`. With a literal dev `url`, tonin knows the URL and appends with
`&` when it already contains `?`.

### Dev: a literal URL

A dev cluster without contract Secrets can point at a shared instance with a literal `url`,
per environment only:

```toml
[database.dev]
url       = "postgresql://postgres:postgres@postgres.shared-dev.svc.cluster.local:5432/identity_dev"
namespace = "shared-dev"                           # egress to the shared instance
labels    = { "app.kubernetes.io/name" = "postgres" }
```

The URL is used as the env var's value (with `tls` set, the TLS parameters are appended and the
CA is mounted, as above). Other environments keep reading the Secret.

### Named databases

`[databases.<name>]` takes the same fields. Defaults are prefixed with the name: env
`<NAME>_DATABASE_URL`, cluster `<svc>-<name>-pg` (so Secret `<svc>-<name>-pg-app`), helper
`TONIN_<NAME>_PG_URI`, CA at `/etc/pg-ca-<name>/ca.crt`.

### Removed in 0.15

tonin no longer renders databases, so these fields fail with a message naming the replacement:
`size` and `version` (set them in the platform layer, e.g. the CNPG `Cluster`), `shared` (every
database is a reference; use a per-env `url` for a dev instance), `name` (use `secret` and
`cluster`/`labels`), and `url` on the base `[database]` table (it is per env). tonin also no longer
adds a `DATABASE_PASSWORD` key to the service's Secret.

Two sections emitting the same env var (e.g. `[secrets].required` listing `DATABASE_URL` while
`[database]` emits it), or an `[env]` key shadowing one, fail generation.

## Using it from sqlx

The framework hands you a URL — you build the pool and thread it through your own handler-state struct, then hand the tonic-generated server to `Service::handler`.

```rust,no_run
use tonin::prelude::*;
use sqlx::postgres::PgPoolOptions;

#[derive(Clone)]
struct AppState {
    db: sqlx::PgPool,
}

#[tokio::main]
async fn main() -> tonin::Result<()> {
    let url = std::env::var("DATABASE_URL").expect("DATABASE_URL set by the rendered Deployment");
    let db = PgPoolOptions::new()
        .max_connections(10)
        .connect(&url)
        .await
        .expect("connect to postgres");

    let _state = AppState { db };
    // let billing_server = BillingServer::new(BillingImpl::new(state));

    Service::new("billing")
        // .handler(billing_server)
        .run()
        .await
}
```

`Service::new` installs the OTel tracer provider (see [05-telemetry.md](05-telemetry.md)). sqlx emits its own spans when an OTel provider is registered — those spans automatically join the request trace, so a single gRPC call shows up as `handler → sqlx::query → postgres`.

## Migrations

Add a `[migrations]` block to control when and how migrations run:

```toml
[migrations]
tool = "sqlx"              # "sqlx" | "refinery" | "flyway" | "custom"
dir  = "migrations/"       # default
mode = "init-container"    # "init-container" (default) | "job" | "none"

[migrations.prd]
mode = "job"
```

`mode` is resolved per environment (`[migrations.<env>] mode` wins):

- `init-container` — an initContainer in every pod of the Deployment runs the migration command
  before the server starts. Simple; every pod (and every replica) runs it.
- `job` — a `<svc>-migrate` Job as a Helm `pre-install,pre-upgrade` hook. Helm applies the rest of
  the release only when it succeeds (with `--atomic`, a failure rolls back). The Job uses the same
  image (digest-pinned when `image.digest` is set), the same database env and CA mount, the
  `[security]` contexts and the service's resources. Its pods carry `app.kubernetes.io/component:
  migrate` and `service.identity`, but not the `app` label the Service selects on, so they never
  receive traffic while the service's network policies still apply.
- `none` — nothing rendered: the service migrates itself, or something else does.

**Hooks run before the chart's own resources exist** (on install) or are updated (on upgrade).
So the Job relies only on what is outside the release:

- the database Secret and CA Secret come from the platform contract;
- `[secrets]` keys are referenced with `optional: true`, because the chart-owned
  `<svc>-secrets` Secret only exists from the first upgrade on (when `secrets.create` is true);
- under Cilium, the Job's own CiliumNetworkPolicy (`<svc>-migrate`: DNS, the otel collector, the
  databases and caches) is a hook with weight `-5`, so it exists before the Job (weight `0`)
  starts. Both are deleted after a successful run and recreated on the next one;
- it runs as the namespace's default ServiceAccount.

For `tool = "custom"`, supply the command:

```toml
[migrations]
tool    = "custom"
command = ["/usr/local/bin/identity", "migrate"]
```

Known tools have their command pre-computed — e.g. sqlx becomes
`["sqlx", "migrate", "run", "--source", "migrations/"]`. A custom tool without a `command` runs
the image's own entrypoint. `run_on` was removed in 0.15: use `mode` (`run_on = "boot"` /
`"manual"` become `mode = "none"`).

## Status (0.15)

- **Ships now** — `Database` trait + `AnyPool` marker in `tonin-sdk::traits`; `[database]` /
  `[databases.<name>]` are platform-contract references (Secret `uri` → `DATABASE_URL`, optional
  `verify-full` CA mount, egress by contract pod labels), with per-env overrides and a dev `url`;
  `[migrations]` renders an initContainer or a hook Job per environment.
- **Not yet**
  - No `Service::with_database` / `Service::database()` accessor; hold your sqlx pool in your own handler-state struct.
  - `AnyPool::pool()` always returns `None`; there is no framework-managed pool.
  - No `tonin-postgres` impl crate. Today the value of `system()` is the only thing other code reads.
- **Plan** — `tonin-postgres` (and friends) implementing `Database` and exposing a managed `sqlx` pool; `Service` accessor wires it.

## Flow

```mermaid
flowchart LR
    H[gRPC handler] -->|state.db.acquire| P[sqlx Pool]
    P -->|TCP 5432| S[(Postgres: platform contract)]
    H -.->|span: rpc.method| T[OTel tracer]
    P -.->|span: db.statement<br/>db.system=postgres| T
    T -->|OTLP| C[Collector]
```

The handler span and sqlx's auto-emitted DB spans share the same trace context because `Service::new` installed the global tracer provider. The collector sees the parent-child link without any per-call wiring.
